# 整体压测：Excel、真实 Verdi 采集、GUI 与互联画布（2026-11-28）

**结论：RTL 与 Excel 功能检查通过，有两项 GUI 稳定性发现（`PASS_WITH_FINDINGS`）。** 全量回归 457 项，失败 0、跳过 0；但在同一进程关闭并重开 GUI 时可复现失效的 Tk 定时回调，同一窗口多轮载入大报告后常驻内存也仍在增长。20,000 行带完整检查结果的离线 GUI 用例通过，用例 27.74 秒，最高单进程 RSS **1.41 GiB**。这个数字不能解读为“2 万行在线全芯片耗时 28 秒”。

## 两项需要跟进的发现

1. **正常关闭窗口后，Tk 定时回调还会触发。** 全量测试日志出现了 4 条 `invalid command name "..._poll_events"`。不用 Excel 或 KDB 也能复现：同一 Python 进程通过应用自己的关闭处理函数开关 8 个真实窗口，得到 8 条相同错误；换进程重做仍是 8/8。应用定期注册 `root.after(100, ...)`，空闲窗口关闭路径会直接销毁 root。建议保存并取消定时器 ID，并用这个探针要求 stderr 干净。未观察到它把 RTL 结果算错；独立进程完全退出后再启动 GUI 不是该复现场景。
2. **同一窗口反复载入大报告有持续内存增长。** 用刚采集的库存回放 30 轮，每轮选择不同组的真实画布，检查通过并执行 Python GC 后读取 GUI 自身的 Linux VmRSS。第一轮 84.8 MiB，第 5 轮 103.2 MiB，第 30 轮 114.1 MiB；第 5→30 轮仍增 **10.9 MiB**，另一次增 **11.0 MiB**。30/30 都正确，不是 OOM，也不足以确认永久泄漏。运行日志在同一窗口会累积；建议优先分开测日志保留量、Tk 分配器和结果模型，再决定是否做日志限长/按需显示。这里是 GUI 自身的轮末内存，不是下文的峰值。

单独复现第一项（同一个已能打开 Tk 的终端）：

```bash
python3 -B scripts/probe_tk_reopen.py 2>tk-reopen.log
grep -c 'invalid command name ".*_poll_events"' tk-reopen.log
```

### 为什么可以确认没有多算 RS 或把画布串组

大设计的预期数不是从程序输出反推的。[测试 RTL](../tests/fixtures/scale_grid.sv) 固定每个 tile 有 32 个 PIPE、2 个子层 RS（OWN 和 LEFT），外加一对 TX/RX。每个 tile 共 36 个物理 RS，其中仅一半 PIPE 贡献拍数。因此 **96 × 36 = 3,456 个物理例化，96 × (16+2+2) = 1,920 拍**。

- 原生 Excel 有 481 个数据行、577 个带保存结果的公式。最先出现的父行只应取得各子层没有认领的 LEFT；每个子层的 OWN 都不能被父行再选中。脚本按完整实例路径逐个比对，还验证所有 3,072 个 PIPE 的奇偶拍数贡献。
- 每个合并区的 TX 和 RX 之间夹一个应被跳过的 97 拍行。预期合计是 2，不是 99。每幅图必须且只能有该 tile 的 `TX.link (output) → RX.link (input)`。此外对 96 个 TX 都检查时钟与复位在预期 CRG 层次的源信号，合计 192 项。
- 这 96 幅大设计画布用的是标量信号。Interface、`mst/slv`、共用一个整体 Interface、两个独立 Interface 在上层连接成员、扇出和不能证明的边，另外用[互联 RTL](../examples/rtl/rs_interconnect.sv)及其真实 GUI/回放测试覆盖；没有把标量结果冒充 Interface 大规模结果。

### 不应通过的输入是否真的被拦下

对同一在线库存注入互不相同的错误：第 2、5 行改错 step，第 3 行同时写错 clk/rst 源信号，第 6 行改错门控标签，第 7 行只清空可选 clk。结果**恰好**是第 2、3、5、6 行 FAIL，第 7 行只有 `EXCEL_FIELD_BLANK` 警告，其他行不受影响。这与“全部绿灯”是不同的验收条件。

主 GUI 脚本还有 83 轮在线、197 轮离线检查，已包括 120 轮同窗口连续离线检查和一次 20,000 行用例；这些次数不能与 457 个不同测试相加当覆盖数。在线用例中，partial KDB 总是保留警告，超深度只报告可证明的来源，只有 clk 而缺少 rst 的负例重复 25 次都不误报 clk 缺失。另有分隔符、多项及部分命中、分组前缀、精确名、中文 route2、已保存/无保存结果的公式、门控参数和 NA 规则、所有配置数据库的导入导出、路径映射等回归。DIV/GATE/OCC 专项检验只沿已配置的输出→输入通路反追，控制端口不因同在该模块就变成时钟或复位源。

## 容量边界

下表是同一离线 GUI 脚本的四个独立进程：用各自的 CSV 规格和生成的 inventory，每行一个独立 position/例化，有参数和时钟追踪证据。计时包含造数据、启动 GUI、检查、读回并展示；不是单独测 Excel 解码，也不是硬件内存用量。

| 离线结果行数 | 用例耗时 | 最高单进程 RSS |
|---:|---:|---:|
| 1,000 | 2.25 秒 | 94.4 MiB |
| 5,000 | 7.34 秒 | 371.2 MiB |
| 10,000 | 12.53 秒 | 730.7 MiB |
| 20,000 | 27.74 秒 | 1,440.6 MiB |

GNU `time` 的 RSS 是任务及其后代中观察到的**最大单进程值**，不是整个 GUI 与全部子进程同时占用的总和，不应当作最低整机配置。独立的 20,000 行原生 XLSX “仅验证”用例最高单进程为 406.1 MiB（包括验收脚本本身）。本轮未测客户全芯片、10 万行、不同 Verdi 版本、24 小时常驻或许可耗尽；也不能由有限次数的取消测试推出绝无泄漏。若要提高支持规模，优先对报告生成、装载和视图显示分别做内存剖析；现有数据不足以把开销归因于某一个组件。

## 一条命令复现

在已经配置好 Verdi 许可、C++ 编译器及 Tk、能正常打开图形窗口的 Linux 终端，进入**含本次变更的项目根目录**，复制：

```bash
PYTHON_BIN=python3 bash scripts/test_vm_project_stress.sh
```

若 Python 3.8 的命令叫 `python3.8`，只替换 `PYTHON_BIN` 的值。脚本自行生成 clean、partial、边界、驱动、互联和规模设计的 elaborated KDB，collector 的输入始终是 `*.elab++`，不需要 filelist 或用户 DUT。不需要 Node 或 Excel；仓库已经包含两个原生 XLSX。

开头打印 `ARTIFACT_DIR=...`；建议预留十几分钟，机器、磁盘、显示器与许可都会影响耗时。本轮结束标记为 `PROJECT_STRESS_PASS_WITH_FINDINGS: metrics.json`：计数、数据一致性等断言已过，但存在诊断项；没有检测到这些现象时才会打印 `PROJECT_STRESS_PASS`。功能断言失败或超时则非零退出。原始 stdout/stderr、各阶段 `.time`、报告和库存留在该次新建的产物目录，失败也不覆盖原始证据。只有脱敏后的汇总适合直接分享；原始报告可能包含本机绝对路径。
